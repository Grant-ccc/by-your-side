## 当前状态

已改用 DeepSeek 官方 API 的 `deepseek-flash`（当前为 DeepSeek-V4.1-Flash），保留角色提示词、近期上下文、回复入库、用量记账、月度文字预算、重复请求去重与错误反馈。2026-10-15 已用独立合成会话完成一次真实调用，验证回复保存、历史读取与重复请求返回已有结果；未上传密钥或测试对话。该检查不代表人物语气、多场景延迟或供应商实扣账单已验收。

本轮默认发消息后立即请求一次回复，不启用作息等待、主动留言、长期记忆、日程执行、图片或安卓通知。原型里的这些能力仍是示例。

当前角色草案 `li-zeyan-v5.2` 将人物底色与聊天规则分开。按所有者对 v5.1 试聊的反馈，改用简短的陪伴回应处理低落开场，收紧随口分享时的追问和作品细节来源，并要求对方想听时把自己的话说完。关系设定为同城各自住的平等恋人，角色可以直接表达在意和自己的偏好。T09 仍有未通过项。

此前 v3 连续试聊发现模型可能违背事件来源约束，以及把轻微打趣写得过硬。v4 在运行时明确标注没有可引用的角色事件，主动分享可从偏好、看法或假设共同活动展开。本轮两段全新三轮合成对话未出现追账式警告或编造已经发生的外出活动，但语气仍需用户反馈。当前约束仍依赖提示词，不是事实校验机制，不能据有限样例宣称这些问题已经彻底解决。

日常语气评阅可按[李泽言人设样本覆盖表](Character-Samples.md#v01-资料覆盖)查找短信、电话旁证和官方情境。样本用于人工对照，T09 以实际三轮聊天和所有者评阅记录为准。

## 2026-11-10 人物语气基线

用项目的 DeepSeek 适配器和运行时提示词直连真实模型。四组各三轮，每组使用独立的内存上下文，组内带上此前往返。共完成 12 次回复，输入 13,570 token、输出 291 token。试聊数据都是虚构场景，调用发生在应用数据库和费用账本之外，供应商用量以 DeepSeek 控制台为准。

| 场景 | 初审记录 |
| --- | --- |
| 日常分享 | 电影第二轮擅自补写了车站镜头里的人已经离开。第三轮收到明确的意见邀请后，能给出对留白结尾的个人偏好。 |
| 低落且不想听建议 | 第一轮复现了咨询式的二选一追问。对方明确只想吐槽后，接下来两轮都保留了陪伴意图。 |
| 轻微打趣 | 三轮都接住了薯片魔术的梗，后两轮顺着观众和请他当托继续聊。 |
| 主动换话题 | 能自己选菜和口味当话题。对方说想先听他讲之后，他讲了自己的做法，但马上把回答义务交回给对方。 |

优先复测普通分享里的事实边界、低落时的第一句，以及对方邀请他继续说时的接话。角色语气以所有者对完整往返的评价为准。

## v5.2 接话复测

所有者认为 v5.1 的电影开场追问和后续影评式措辞都有明显的 AI 味，尤其不接受低落开场的二选一。对照尝试了缩短提示词和隔离试跑 Flash 思考模式，电影与看展的开场仍会追问。部分试稿还把未确认的经历写成了角色的过去。最终保留局部接话调整，沿用项目原有的模型调用方式。

最终版用真实 DeepSeek 复跑原四组各三轮，另加看展和低落两组各两轮。16 条回复均成功返回，使用合成场景和组内上下文，在应用数据库和费用账本之外运行。原低落开场改为直接陪伴。新低落场景开场仍擅自安排休息，收到只想聊天的说明后能接住。对方说想先听他说时，他继续讲了自己的偏好。电影第二轮没有再补写镜头里的动作，但电影和看展仍出现分析式判断及问句，包括二选一。T09 的日常接话仍未通过。

## 偏好样本对照

把试聊反馈整理为两组有完整往返的相对偏好样本、一组待定样本，以及只有负面反馈的例子。两组偏好都来自轻松闲聊。待定及单侧负例暂不作为示范。训练材料与留出输入分开保存在本机 `.local/`，检查了标识、两边轮次和输入是否重合。

用现有 `deepseek-flash` 和 v5.2，在四组新的合成场景上对照原提示词与附加两组偏好样本的提示词。每组每种方式各聊两轮，共 16 次调用。加入样本后，取快递场景的两次追问消失，猫抢被子的场景增加了两次追问。两种方式各八条回复，索取进一步回答的问句都出现三次。加入样本后，电影场景的二选一消失，但猫抢被子的场景出现了二选一。低落场景仍用比较泛的陪伴话术。每种方式在每个场景只生成一条路径，这批对照未显示稳定改善。

这轮用偏好样本做上下文对照，模型权重没有变化。实验使用项目模型适配器，在应用数据库与费用账本之外执行，结果留在本机。

## 四组三轮底座对照

从[已评阅的示范](Character-Dialogues.md)取 A 市集买杯子、D 聊煎蛋两段，各三轮，共六条角色回复。以 `messages` 格式导出监督微调数据。另写四个新场景，每组三轮，分别观察分享、低落、打趣和请他主动开话题。按完整场景留出，核对了用户消息无重合。数据、输入和原始回复保存在本机 `.local/persona-baseline-v1/`。

两个底座在 CPU 上使用同一份 v5.2 角色提示词，加上本次没有角色日程及外出事件的说明。固定贪心解码，每轮最多 80 个新 Token。Qwen3 关闭思考。每组从独立对话开始，后续轮次带入本模型自己的前文。各生成 12 条回复。

| 场景 | Qwen2.5-0.5B-Instruct | Qwen3-0.6B |
| --- | --- | --- |
| 日常分享 | 第二轮原样复述她的书签描述，第三轮也沿用了她的问句开头。 | 三轮都把她拿书签、没买书的经历说成自己的。 |
| 低落陪伴 | 首轮表示愿意陪她，第二轮追问花怎么了，第三轮重复首轮。 | 三轮都只回「有」。 |
| 轻微打趣 | 反复把酸奶占领冰箱理解成收藏，错过她第三轮转认真。 | 把谈判玩笑接成冷藏温度建议，三轮反复提议帮忙。 |
| 主动开话题 | 首轮把话题交回给她，她请他接着说时又追问她的计划。 | 前两轮重复提示词中的示范句，第三轮仍把话题交回给她。 |

24 条均自然结束在输出上限前。两款小底座都在多轮中丢失说话人或话题，因此这批结果保留为后续对照。下一轮候选模型继续用同一批场景检查说话人、接话和连续性。当前训练稿只覆盖日常分享和主动开话题。

### Qwen3 4B 候选筛查

在同一批四组三轮上运行 Qwen3-4B-Instruct-2507 的 Q4_K_M 量化版本。使用 Ollama 的本机接口，按角色、用户、助手的顺序传入原对话。上下文上限 4,096，输出上限 80 Token，温度为 0。Unsloth 发布的量化文件从 ModelScope 下载，SHA-256 与发布者的文件记录一致。[Qwen 官方模型](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507) · [量化文件校验值](https://huggingface.co/unsloth/Qwen3-4B-Instruct-2507-GGUF/blob/main/Qwen3-4B-Instruct-2507-Q4_K_M.gguf)

使用 v5.2 时，模型可以给出自己的选书偏好，能延续酸奶的谈判玩笑，也能在被邀请时讲同一个话题。书签、枯花和主动分享三组都出现了无来源细节。它补了纸片上的字，声称自己看过那盆花，还编出刚煮咖啡、以前买过肉桂和她曾说过的口味。主动分享组有两条达到输出上限。

同一量化文件、解码设置和场景下，换一份简短提示词再跑 12 条。提示词明确谁是说话人、当下可引用哪些事实，以及怎样用偏好或假设开话题。第二次把咖啡话题说成想象中的搭配，纸片文字和花的状态也以她说出的细节为限。书签场景仍猜测她为什么拿走纸片，低落时用花解读她的情绪，打趣和主动分享仍出现过长的回复，各有一条达到输出上限。两份结果均留作人工对照，原始回复和简短提示词在本机 `.local/persona-baseline-v1/`。

4B 在这批场景比两个小模型更能把话题接下去，事实边界和短信语气仍需校准。将它留作后续微调候选。正式做训练前后的对照时，需从同一份可训练权重开始，并用同一条件生成两组回复。

## 本机 LoRA 小样本试验

训练脚本在项目根目录的 `scripts/train-persona-pilot.py`。输入是本机 `.local/` 的偏好对照和独立留出场景。使用 Qwen2.5-0.5B-Instruct 的公开权重，在 CPU 上冻结底座，只训练注意力查询和值矩阵旁的 LoRA 参数。训练对比同一段合成对话下的两条路径，按用户评过的偏好调整角色回复的分数，用户消息只作为上下文。未确认的样本继续留在评阅材料中。模型权重来自 Qwen 的 ModelScope 仓库，SHA-256 与 Qwen 在 Hugging Face 发布的权重一致。[Qwen 模型](https://modelscope.cn/models/Qwen/Qwen2.5-0.5B-Instruct) · [官方权重校验值](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct/blob/main/model.safetensors)

复跑使用隔离环境中的 `torch==2.8.0+cpu`、`transformers==4.57.6` 和 `peft==0.18.1`。每次指定新的输出目录，避免覆盖旧实验。

```powershell
& .local/persona-venv/Scripts/python.exe scripts/train-persona-pilot.py `
  --model-dir .local/qwen2.5-0.5b-instruct `
  --pairs .local/persona-preferences.json `
  --holdout .local/persona-holdout.json `
  --output .local/persona-pilot-next
```

2026-11-10 在本机跑完 8 步。两组偏好轮流用于训练，共更新 270,336 个 LoRA 参数。伞场景中，已选路径相对于另一条路径的对数概率差从 −7.91 变为 79.00。这个数值只说明模型更偏向见过的训练答案。

四组留出场景各比较两轮。微调后的模型仍会把对方做过的事说成自己做的，也会忽略她已经描述的情节或低落情绪。未观察到稳定的角色语气改善。检查点和完整报告在 `.local/persona-pilot-01/`，用于复现实验。T09 仍未通过。

同一个底座也跑了 8 步监督微调。复跑命令增加 `--objective sft`，并另指定输出目录。训练只计算用户选中的角色回复，其余版本用于前后评分。训练样本上的偏好分数提高，四组留出场景的未训练基线与上一轮完全一致。两种微调都未解决说话人混淆。监督微调后，模型把用户挪被子的动作说成自己的动作，也在用户明确只想聊一会儿时重复提出帮忙。监督微调的检查点和结果留在 `.local/persona-pilot-sft-01/`。

同样的四组对话也用于筛查未微调的 Qwen3-0.6B。在本机以 BF16 加载，并在聊天模板中关闭思考。初次生成使用模型默认采样参数，出现复述和说话人混淆。另以固定的贪心解码对照原提示词和明确区分两位说话人的提示词。两种提示都在电影场景把用户的观影经历复述为模型自己的经历，猫抢被子的两轮也重复了用户的话。Qwen3 的原始输出保存在 `.local/persona-qwen3-role-check.json`。两个本机小底座在这批场景中都没有达到接入标准。[Qwen3 模型说明](https://huggingface.co/Qwen/Qwen3-0.6B)

## Flash 与 Pro 两轮盲测

2026-11-10 使用同一份 v5.2 提示词、相同的虚构用户消息和非思考模式。对照四组旧场景和四组新场景，每个模型在每组独立保留自己的前一轮回复。两边各生成 16 条，共 32 条。A、B 按场景打乱，盲评稿和模型对应关系分开保存在本机。[DeepSeek API 模型配置](https://api-docs.deepseek.com/api/create-chat-completion/)

两边在取快递、看电影和猫抢被子的场景都保留了说话人。请他主动讲小事时，两边都提到了前文未提供的个人经历。这组留作故障对照。其余场景仍可见例行追问、擅自解释感受和给建议的情况，角色语气等待所有者盲评。实验单独调用模型接口，App 的 Flash 费用规则和日常聊天入口沿用现行配置。

## 主动话题的事实边界

2026-11-10 用 DeepSeek Flash 非思考模式和 v5.2 提示词单独复测。四组虚构用户消息各聊两轮。基线有三组至少一轮把未提供的具体经历、现实安排或过去的个人经历当成事实。一次给出三条已核过的角色偏好后，这类错误降到一组，但四组第一句都选了电影，两组在用户说想继续听时换了话题。[角色样本 D01、D09 和 N03](Character-Samples.md)

接着给每组人工指定一条偏好，并要求第二轮沿用上一条的细节。原四组加两组新场景都聊了两轮。六组都保留了原话题，一组仍虚构了刚才翻过片单。等待水烧开的一组擅自把话引到对方弹琴，送礼场景有重复解释。这次只验证到话题能在这批样本中延续，仍需检查事实边界与短信语气。测试在 App 外完成，未实现自动选题，也未修改日常聊天提示词。

## 本机配置

1. 在 [DeepSeek 开放平台](https://platform.deepseek.com/)创建 API Key，确认 API 账户余额；网页登录聊天与 API 计费是不同入口。
2. 在被 Git 忽略的 `.env.local` 填写以下变量，保留原有数据库配置：

```dotenv
DEEPSEEK_API_KEY=在本机填写真实密钥
AI_MODEL=deepseek-flash
AI_MONTHLY_LIMIT_CNY=20
```

3. 执行 `npm run db:migrate`，停止旧开发服务，再运行 `npm run dev`。
4. 页面刷新后显示“DeepSeek已配置”。这只表示本机有配置，实际可用性以真实调用结果为准。发送少量非敏感测试消息，检查回复、刷新后的历史和 DeepSeek 用量。

后端默认使用 `https://api.deepseek.com`，不需要业务空间 ID。可选 `AI_BASE_URL` 仅接受此官方地址或其 `/v1` 路径，拒绝其他域名。旧的百炼变量不再读取；不将百炼密钥转发给 DeepSeek。旧配置若包含 `AI_BASE_URL`，需改为 DeepSeek 官方地址或删除该项。

密钥不填聊天、不上传 GitHub、不放 `VITE_` 环境变量，也不打包进安卓。启用模型后，角色提示词和最近一段聊天会发给 DeepSeek；数据库与 GitHub 同步是不同的数据去向。服务仍只允许本机开发访问，尚无生产登录。

## 一条回复如何产生

用户消息先独立保存，随后客户端请求回复。服务端校验会话与来源消息归属，以数据库命名锁串行处理同一会话；预算记录锁在事务内预留额度，提交后才调用模型。成功后将回复、Token 用量与费用结算一次提交。回复用 `reply_to_message_id` 唯一约束去重。

历史上下文最多读取最近24条，再限制文本总量；旧消息仍在数据库，但不保证每次都进入模型。当前没有摘要或长期记忆，不能承诺永久记住所有对话。角色提示词在 `apps/server/src/character.ts`，是项目原创适配，并非官方台词库。

模型使用非思考模式、非流式单次返回，最多512输出 Token。页面只在真实请求进行时显示“正在输入”，不会伪装角色已读。刷新只读取记录与任务状态，不自动发起付费生成。

## 费用与失败

初期月度文字预算默认20元，可在本地调整至不超过50元；此处是工程默认值，不含图片、服务器或其他服务。月度按北京时间计算。

费用按2026-10-15核对的 DeepSeek Flash 高峰、缓存未命中价格保守估算：输入2元/百万 Token、输出8元/百万 Token。官方空闲时段价格减半，缓存命中输入另有优惠；当前预算账本统一按较高单价计算，不追踪假日或缓存优惠，可能提前达到本地预算。成功后按模型返回的 Token 用量缩减预留，得到的仍是费用上限估算，数据库历史字段 `actual_cost` 也不代表供应商实扣账单。实际费用以 DeepSeek 控制台为准。价格或模型变化需要重新核对成本策略，暂不开放任意模型名称。

- 已保存的回复再次请求时返回原记录，不重复调用模型。
- 明确拒绝的配置或限流错误释放预留；用户手动重试才启动新一次尝试。
- 连接中断、异常响应、回复不完整或用量无法确认时，不自动重试。费用暂按预留上限计入，`actual_cost` 保留为空，实际账单以 DeepSeek 为准。
- 进程在调用期间中断时，保留 `running` 与额度预留，阻止同一会话继续生成；需要开发者核对供应商账单和本地任务后修复，当前没有自动对账或恢复按钮。
- 预算不足时停止新增生成，消息仍可保存。该限制仅覆盖本应用经此后端发起的文字调用，不能约束其他应用使用同一个密钥。
